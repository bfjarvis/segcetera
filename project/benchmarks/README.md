# Benchmarks

Development-only performance comparisons using [bench](https://bench.r-lib.org/).
This directory is excluded from package builds through the existing `project/`
exclusion. Install `bench` separately; it is a development tool here.

## Grid search

`grid-search.R` compares brute, boost, and grid search on the same square-lattice
pattern generated by `seg_pattern()`. That generator retains a subset of its
candidate locations, so some lattice cells are unoccupied. The default workload
has 10,000 agents, three groups, three radius bands, and normalized biweight
weights with power 3. Edit the settings at the top to change the workload,
including population-based kNN.

The script first checks agreement of both local environments and indices. It
then times indices-only calls, including input preparation, search construction,
weights, and index calculations. Pattern generation is outside the timed calls.
All timed iterations contribute to the summary, including garbage collection.

Run from the repository root using a fresh R session and an optimized installed
build. `devtools::load_all()` commonly uses debug compilation, which changes
timings substantially. For example, from a terminal:

```sh
mkdir -p /tmp/segcetera-benchmark-library
R CMD INSTALL --preclean --library=/tmp/segcetera-benchmark-library .
R_LIBS_USER=/tmp/segcetera-benchmark-library Rscript --vanilla project/benchmarks/grid-search.R
```

This private library preserves your ordinary package installation. Retain the
installation output when investigating compiler differences. The script records
R's configured compiler and flags; user Makevars and environment overrides are
visible in the installation output. In a fresh console, select the private
library before sourcing the script:

```r
.libPaths(c("/tmp/segcetera-benchmark-library", .libPaths()))
source("project/benchmarks/grid-search.R")
```

## Radius crossover

`radius-crossover.R` holds the generated 10,000-agent pattern fixed and compares
brute with boost for single radii from 0.5% to 40% of the square's side length.
Each radius gets five timed iterations per backend, with backend order
alternating between radii. Full environments and indices are checked before
timing indices-only calls. Settings are at the top of the script.

It estimates the fraction of input points retained within each radius using
256 sampled focal locations. This incorporates clustering and boundary effects
alongside the radius/side ratio. The output plot shows brute time divided by
boost time: values above one favor boost. A crossover is a workload- and
machine-specific observation; changing N or the spatial distribution can shift it.

Run with the same private library setup:

```sh
R_LIBS_USER=/tmp/segcetera-benchmark-library Rscript --vanilla project/benchmarks/radius-crossover.R
```

Optional command-line arguments set N, timed iterations, and radius/side
fractions. For a focused larger run with two timed repeats at each radius:

```sh
R_LIBS_USER=/tmp/segcetera-benchmark-library Rscript --vanilla project/benchmarks/radius-crossover.R 100000 2 0.02 0.05 0.10 0.15
```

The CSV is updated after each radius. Larger datasets and broad radii can take
substantial time, including the agreement checks and untimed allocation runs.

## Radius-by-size matrix

`radius-search-matrix.R` measures a fixed square-lattice pattern at each N,
crossing 1,000, 2,500, 5,000, 10,000, 20,000, 40,000, and 80,000 agents with the
default distance bands. The default `band_basis = "distance_quantile"` uses
`seg_default_bands()` and its default `probs`, currently 0.01, 0.025, 0.05, 0.1,
0.15, 0.2, 0.25, 0.3, 0.4, and 0.5. These are quantiles of sampled pairwise
distances; each N has its own calculated radii. Each cell has three timed repeats per
backend. Pattern generation and sampled neighbor counts are outside the timed
calls; input preparation, search setup, and indices remain inside. `bench`
checks index agreement for each cell. The earlier focused benchmark also
checks full environments.

```sh
R_LIBS_USER=/tmp/segcetera-benchmark-library Rscript --vanilla project/benchmarks/radius-search-matrix.R
```

The script saves a checkpoint and timing CSV after every cell. Rerunning it
resumes completed cells when settings and installed R/native code checksums
match. Change `run_name` for a different experiment, or set `resume = FALSE`
to replace the previous run. Keep other CPU-intensive jobs idle while timing.
The 80,000-agent cases at the broadest bands can take substantial time.

Set `band_basis = "side_fraction"` to use `radius_fractions` instead, reproducing
the earlier scan with radii from 1% through 40% of the square's side. Set
`agent_counts` back to the earlier values to cap that experiment at 20,000.
Choose a fresh `run_name` when changing these settings; the new default-band
scan saves separately from the earlier side-fraction results.

Two heatmaps show percentage and absolute time saved by boost relative to
brute. Positive values favor boost; negative values favor brute. Tiles show
measured combinations, with no interpolation between cells. Columns correspond
to distance percentiles or side fractions according to `band_basis`. The CSV
includes actual radii, percentages of side length, and sampled neighbor fractions.
The result is an exploratory heuristic for this pattern, kernel, and machine.
Small timing differences deserve further repetitions before informing defaults.

For the categorical, normalized-biweight workload tested here, brute is a useful
radius-search default. A maximum radius below roughly the 10th percentile of
point distances is a useful prompt to benchmark boost, particularly for larger
datasets. The 5th through 10th percentiles form a transition zone in these runs. These
are single-band measurements; a joint multi-band call shares search work and
benefits from its own timing comparison. Geometry, population distribution,
variable specifications, and hardware also influence the crossover.

## Shared cases

`cases.R` compares one shared-case call with separate calls for four populations
on common square-lattice support, using each search backend with radius and kNN
neighborhoods. It checks index agreement and the number of focal searches before
reporting end-to-end timings, including case alignment and input preparation.
Settings are at the top of the script; use the same optimized private-library
setup as the other benchmarks.

## Results

Each run saves a timing CSV, an RDS containing raw bench results and settings,
and a text record of the session under `results/`. These machine-specific files
are ignored by Git. Provenance includes the source commit, working-tree status,
installed package path/version, compiler configuration, and grid diagnostics.

`mem_alloc` and `r_allocated_bytes` describe allocations on the R heap. Native
C++ allocations require a separate memory profiler for a complete assessment.
They are allocation totals rather than peak resident memory. Compare timings
on the same machine and build, and repeat runs before drawing conclusions from
small differences.
